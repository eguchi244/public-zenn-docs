# 下書きから公開までの手順

> このスキルは同じ基準で構成された Zenn リポジトリ間で共通。**どのリポジトリが下書き用で、どれが公開用か**、原本と公開先の slug の対応は `.claude/zenn-profile.md` の「下書きと公開の流れ」にある。まずそこを読む。

## 考え方

- **原本は下書き用リポジトリに置き続ける。** 公開用リポジトリの記事・本は、原本から同期して作る**写し**。公開後の修正も原本で行い、同期し直す
- 書きかけの記事・本を公開用リポジトリに置かない。公開用リポジトリは `published: true` で運用しており、`main` に入った時点で公開される
- **原本の slug は `<公開slug>-draft`** にする。下書き用リポジトリも Zenn に連携していると、そちらを push するたびに原本がデプロイされる。公開側と同じ slug だと、公開中の本を非公開や古い内容で上書きするか、デプロイエラーになるおそれがある
- 教材リポジトリとのつながり（submodule・版の記録）は下書き用リポジトリにある（`source-material` スキル）。原本を下書き側に置くのはこのため

## 1. 下書き用リポジトリで原本を書く

- 公開時の slug を `CLAUDE.md` の「slug の付け方」に従って先に決め、原本は `<公開slug>-draft` で作る（例: `npx zenn new:book --slug js-timer-tutorial-eguchi244-draft`）
- `published: false` のまま書く
- 区切りごとに `commit-flow` スキルでコミットする。`published: false` なので下書き用リポジトリの `main` に入れても公開されない
- 本の画像は下書き用リポジトリの方針（プロファイルの「画像ディレクトリの方針」）のまま置いてよい。公開側の方針への移し替えは 4 の同期スクリプトが行う

## 2. 公開先の構成を把握する

初めて公開する前に、公開用リポジトリの既存の記事・本を**実際に数本読み**、次を確認する。プロファイルの「記事の構成」に要点があるが、要約で済ませず原文を見る。

- frontmatter（`emoji`・`type`・`topics`・`published` の書き方、コメントの有無）
- 見出しの型（冒頭・結びの節、小見出しの番号の振り方、見出しレベルの使い方）
- 本の場合は章タイトルの書式と章冒頭の書き出し
- Zenn 記法（`:::message`・`:::details` など）の使いどころ

```bash
ls articles books/*/                       # 公開用リポジトリで
grep -n '^#' articles/<似た記事>.md        # 見出し構成。コードブロック内の # コメントも拾うので中身も読む
```

## 3. 原本を公開先の型に揃える

揃え込みは**原本側で行う**（公開側で直すと次の同期で消える）。

- **構成・書式を公開先に揃える。** 2 で把握した frontmatter・見出しの型・章タイトルの書式との差分を直す。見出しの組み替えや大きな書き直しになる場合は、直す前にユーザーに確認する
- **`config.yaml` を両方の zenn-cli で通る書き方にする。** プロファイルの「config.yaml の現状」を見る（`chapters:` は書かない）
- 下書き用リポジトリで `npx zenn preview` を起動して確認し、`commit-flow` でコミットする

## 4. 公開用リポジトリへ同期する

公開用リポジトリで `git switch -c feature/<内容>` してから、同期スクリプトを実行する。

```bash
python -I <下書き用リポジトリ>/.claude/skills/draft-to-publish/scripts/sync_book.py \
  <下書き用リポジトリ> <公開用リポジトリ> <下書きslug> <公開slug>
# Windows の Python に渡すパスは cygpath -w で変換する
```

スクリプトがすること:

- 公開側の `books/<公開slug>/` と `images/<公開slug>/` を**まるごと作り直す**（公開側で直接編集した内容は消える）
- `config.yaml` の `published: false` を `true` にする
- 本が参照する `/images/<ディレクトリ>/` を `images/<公開slug>/<ディレクトリ>/` へコピーし、参照パスを書き換える（公開側の本の画像は `images/<本の slug>/<章ファイル名>/` の2階層。実物は `ls images/<既存の本の slug>/` で確かめる）
- 原本の slug と公開 slug が同じなら中止し、参照切れがあれば失敗する
- 改行コードを保つ（バイト単位で処理）

記事（`articles/`）にはまだ対応していない。記事を公開するときは同じ考え方で手作業で行い、必要ならスクリプトを拡張する。

同期後に `git status` と `git diff` で、意図した変更だけが出ていることを確認する。**初回公開でなければ、差分は原本で直した箇所だけのはず。** それ以外が出たら公開側で直接編集されていた可能性があるので、ユーザーに確認する。

## 5. プレビューで確認する

```bash
npx zenn preview     # 公開用リポジトリで。エラーが無く、画像が表示されること
```

## 6. コミットしてマージする（＝公開）

`commit-flow` スキルに従う。件名は初回が `[<記事・本の名前>]を投稿`、修正なら `[<名前>]を修正`。本文に同期元の原本のコミットと、元にした教材の版（`教材: <リポジトリ>@<短縮ハッシュ>`）を書く。

**`main` へのマージがそのまま公開になる。** マージ前にユーザーへ「マージすると公開されます」と一言確認する。

## 7. 公開後

- 原本は**消さない**。公開後の修正も原本で行う
- **公開用リポジトリの記事・本は直接編集しない。** 直したいことがあれば原本を直して同期し直す
- 原本と公開先の slug の対応を、両方のプロファイルの「下書きと公開の流れ」に記録する

## 公開後の修正

教材の修正がきっかけの場合（多くはこれ）:

1. 教材リポジトリで修正し、commit・push する（教材リポジトリ側の `commit-flow`）
2. 解答コードが変わったなら、`answer-repo` スキルで答え合わせ用リポジトリの章ブランチを更新する
3. 下書き用リポジトリで feature ブランチを切り、`source-material` スキルで submodule を最新化して、前回の版からの差分を確認する
4. 差分に合わせて原本を直し、`npx zenn preview` で確認して `commit-flow` でコミットする（参照の更新も同じコミットに入れる）
5. 公開用リポジトリで 4〜6 を行う（同期 → プレビュー → マージ＝公開）

本の文章だけを直す場合は 3 の最新化を飛ばし、4 から行う。

修正の履歴は、どちらのリポジトリでも `--no-ff` のマージコミットとして `main` に残るので、ブランチを消しても追える（`git log --oneline -- books/<slug>/`）。
