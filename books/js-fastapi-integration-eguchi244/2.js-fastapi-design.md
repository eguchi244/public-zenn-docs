# フロントとバックをつなぐ設計
第2章では、入門01の要件をもとに、アプリの構成・API の呼び出し方・エラー処理の方針を設計します。

前作の2冊と違い、この書籍では**新しく作る画面や API はほとんどありません**。設計の中心は「既存の画面と API を、どこで・どうつなぐか」です。

# ①ファイル構成
フロントエンドとバックエンドを**独立したプロセス**として動かすため、フォルダも分けます。

```
js-fastapi-task/
├── backend/
│   ├── venv/            # 仮想環境（入門03で作る）
│   ├── main.py          # FastAPI のプログラム（前作の完成版 + CORS 設定）
│   ├── requirements.txt
│   └── tasks.db         # SQLite のデータベース（起動時に自動で作られる）
└── frontend/
    ├── index.html       # 画面（前作の完成版を改修）
    ├── style.css        # スタイル（ローディング・エラー表示を追加）
    └── script.js        # fetch による API 通信に書き換える
```

# ②アーキテクチャ
画面は Live Server、API は Uvicorn と、**別々のサーバーから配信**されます。

```
ブラウザ（Live Server :5500）
  └─ frontend/script.js
       │  fetch('http://localhost:8000/tasks', ...)
       ▼
FastAPI サーバー（Uvicorn :8000）
  └─ backend/main.py
       └─ SQLite（tasks.db）
```

ポート番号が違うので、ブラウザから見るとこの2つは**別のオリジン**です。このままでは通信がブロックされるため、API 側で CORS の設定をします（次の③）。オリジンと CORS の詳しい説明は、実際にエラーを見てから入門03で行います。

# ③CORS 設定（backend/main.py）
FastAPI の `CORSMiddleware` で、次のオリジンからの通信を許可します。

| 許可するオリジン | 用途 |
|------------------|------|
| `http://127.0.0.1:5500` | Live Server（IP アドレス形式） |
| `http://localhost:5500` | Live Server（ホスト名形式） |
| `http://127.0.0.1:5510` | Live Server の代替ポート（IP アドレス形式） |
| `http://localhost:5510` | Live Server の代替ポート（ホスト名形式） |

- メソッドとヘッダーは、すべて許可する
- `127.0.0.1` と `localhost` の両方を書く
  - `allow_origins` は完全一致で照合され、ブラウザにとってこの2つは別のオリジンになるため
  - どちらの形式でページが開かれるかは、ブラウザや環境によって異なる
- 代替ポートの 5510 番も許可する
  - 開発機によっては 5500 番が使えず、Live Server のポートを変えて起動することがあるため

# ④API の呼び出し方
## 呼び出す API
ベース URL は定数 `API_BASE`（`'http://localhost:8000'`）にまとめます。API 本体は前作から変えません。

| 操作 | 関数 | メソッドとパス | リクエストボディ | 成功時のレスポンス |
|------|------|----------------|------------------|--------------------|
| 一覧取得 | `fetchTasks()` | `GET /tasks` | なし | 200・タスクの配列 |
| 追加 | `addTask(title)` | `POST /tasks` | `{ "title": "買い物" }` | 201・作成したタスク |
| 完了状態の更新 | `toggleTask(id, completed)` | `PUT /tasks/{id}` | `{ "completed": true }` | 200・更新したタスク |
| 削除 | `deleteTask(id)` | `DELETE /tasks/{id}` | なし | 200・`{ "ok": true }` |

## タスクのデータ
API が返すタスク1件の JSON は次の形です。

```json
{
  "id": 1,
  "title": "買い物",
  "completed": false,
  "created_at": "2026-10-16T09:00:00"
}
```

前作の画面のタスクオブジェクトとは、2か所が違います。

| 項目 | 前作の画面 | API |
|------|-----------|-----|
| ID | `id`（文字列。`crypto.randomUUID()` で作る） | `id`（数値。データベースが自動で振る） |
| 作成日時 | `createdAt`（camelCase） | `created_at`（snake_case） |

JSON のキー名は、**データを持っている側（サーバー）の命名に従います**。Python の慣習は snake_case なので、フロントも `created_at` で受け取ります。

## 4つの関数に共通するルール
- レスポンスの `res.ok` が `false` なら、`Error` を投げる
  - `fetch` は 404 や 500 が返っても例外にならず、`res.ok` が `false` になるだけなので、自分で例外に変える
  - 投げた例外は、後述の `apiCall` が受け止めて画面に表示する
- 書き込み系（追加・完了状態の更新・削除）は、成功したら最後に `fetchTasks()` で一覧を取り直す
  - フロント側の配列も書き換えて画面を合わせると、正しいデータの置き場所がサーバーとフロントの2つになり、食い違うおそれがあるため
  - サーバーを唯一の正として、画面は常にサーバーから取り直した一覧で描く
- 完了状態の更新は、`completed` だけを送る部分更新にする

# ⑤前作の画面からの変更点
| 変更前（前作の画面） | 変更後（この書籍） |
|---------------------|-------------------|
| `tasks` 配列を状態として持つ | 状態を持たず、API のレスポンスをそのまま描画する |
| `localStorage` に保存 | API サーバー（SQLite）に保存 |
| 同期的に配列を書き換えて描画 | `async` / `await` で通信の完了を待ってから描画 |
| 正しいデータの置き場所 = JS の配列 | 正しいデータの置き場所 = API サーバー |
| フィルタータブで絞り込み | **フィルタータブは外す** |
| 失敗しない前提の画面 | ローディング表示・エラー表示を追加（通信は失敗しうるため） |

:::message
フィルタータブ（すべて / 未完了 / 完了済み）を外すのは、この書籍を**通信の作法に集中させる**ためです。API には `GET /tasks?completed=true` のように完了状態で絞り込む機能があるので、タブを戻したくなったら、選んだタブに応じてクエリパラメータを付けて一覧を取り直せば実現できます。
:::

# ⑥エラーハンドリングの方針
すべての API 呼び出しは `apiCall(fn)` を通し、ローディング表示とエラー処理をここにまとめます。

```
apiCall(fn)
  → 前回のエラー表示を消す
  → ローディング表示（通信中...）を出す
  → fn()（API を呼ぶ処理）の完了を待つ
      失敗（例外）:
        → コンソールにエラーの内容を出す
        → 画面に「サーバーとの通信に失敗しました」を表示する
  → 成功・失敗のどちらでも、ローディング表示を消す
```

- ローディング表示を消す処理は `finally` に置く
  - 成功・例外のどちらの経路でも必ず消えるようにするため
- エラーはコンソールだけでなく画面にも出す
  - コンソールだけでは、利用者が失敗に気づけないため
- ページ読み込み時の一覧取得も、`apiCall(fetchTasks)` として同じ経路を通す

# ⑦関数設計
| 関数名 | 役割 |
|--------|------|
| `fetchTasks()` | `GET /tasks` で一覧を取得して `render` に渡す |
| `addTask(title)` | `POST /tasks` でタスクを作成し、`fetchTasks` で取り直す |
| `toggleTask(id, completed)` | `PUT /tasks/{id}` で完了状態だけを部分更新し、`fetchTasks` で取り直す |
| `deleteTask(id)` | `DELETE /tasks/{id}` でタスクを削除し、`fetchTasks` で取り直す |
| `showLoading(isLoading)` | ローディング表示（通信中...）の表示・非表示を切り替える |
| `showError(message)` | エラーメッセージを画面に表示する |
| `clearError()` | エラー表示を消す |
| `apiCall(fn)` | API 呼び出しを包み、ローディング表示とエラー処理を一元化する |
| `render(tasks)` | 引数で受け取った一覧で画面を描き直す（状態変数を持たない） |
| `createTaskElement(task)` | タスク1件分の `<li>` 要素を作って返す（前作のまま） |

## イベントハンドラー
| 関数名 | 役割 |
|--------|------|
| `handleTaskSubmit(event)` | フォームの送信を受け、入力チェック → `apiCall` で `addTask` → 成功したら入力欄を空にする |
| `handleTaskListClick(event)` | 一覧のクリックをデリゲーションで受け、`data-action` に応じて `apiCall` で `deleteTask` / `toggleTask` |

# ⑧完成コードの全体構造
```
backend/main.py   ← 前作の API + CORSMiddleware（allow_origins に Live Server の4オリジン）
frontend/
├── index.html    ← 前作の画面 + ローディング/エラー表示欄（フィルタータブは外す）
├── style.css     ← 前作のスタイル + .loading / .error / .hidden
└── script.js
     ├── API通信: fetchTasks / addTask / toggleTask / deleteTask（書いたら取り直す）
     ├── 通信UI: showLoading / showError / clearError / apiCall（try-catch-finally の一元化）
     ├── 描画: createTaskElement / render(tasks) ← 状態を持たず引数で受け取る
     ├── イベントハンドラー: handleTaskSubmit / handleTaskListClick（すべて apiCall 経由）
     ├── イベントリスナー: form submit / タスク一覧の click（イベントデリゲーション）
     └── 初期表示: apiCall(fetchTasks)
```

# まとめ
設計のポイントは、次の3つです。

- 画面と API は**別のオリジン**から配信されるので、API 側で CORS の許可が要る
- 正しいデータの置き場所は**サーバーだけ**。画面は書き込んだら必ず取り直す
- 通信は失敗しうるので、ローディングとエラーの表示を `apiCall` に一元化する
