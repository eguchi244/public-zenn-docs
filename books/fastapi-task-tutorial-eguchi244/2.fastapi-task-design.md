# タスク管理APIの設計
第2章では、コードを書くまえの準備としてタスク管理 API の設計を行います。

API の設計で決めることは、「どの URL に、どの HTTP メソッドで、何を送ると、何が返ってくるか」「データをどんな形で持つか」「リクエストが届いてから返すまでに何が起きるか」です。ここで決めたことを、入門03以降で順番にコードにしていきます。

:::message
この章は完成版（入門06まで終えた状態）の設計です。今の時点ですべてを理解できなくても大丈夫です。実装中に迷ったら、この章へ戻ってきてください。
:::

# ③エンドポイント設計
| メソッド | URL | 送るデータ（リクエストボディ） | 成功時のステータス | 返すデータ | 説明 |
|----------|------|----------------|------------------|------------|------|
| GET | `/tasks` | — | 200 | `Task` の配列 | 一覧（`?completed=true/false` で絞り込み可）。ID の昇順で返す |
| GET | `/tasks/{id}` | — | 200 | `Task` | 1件取得（存在しなければ 404） |
| POST | `/tasks` | `TaskCreate` | **201** | `Task` | 新規作成 |
| PUT | `/tasks/{id}` | `TaskUpdate` | 200 | `Task` | 部分更新（存在しなければ 404） |
| DELETE | `/tasks/{id}` | — | 200 | `{"ok": true}` | 削除（存在しなければ 404） |

- **POST だけ 201 を返す:** 「新しいデータを作った」ことを `201 Created` で表すのが REST API の慣習です。FastAPI の既定は 200 なので、明示して変えます
- **DELETE は `{"ok": true}` を返す:** 本文の無い `204 No Content` も選択肢ですが、成功したことを JSON で受け取れるほうが、画面側のプログラムから扱いやすいためです

## 失敗したときの返し方
| 状況 | ステータスコード | 返すデータの例 | 誰が返すか |
|------|-----------------|-------------|------|
| 存在しない ID へのアクセス（GET / PUT / DELETE） | 404 Not Found | `{"detail": "Task not found"}` | 自分で書く（`get_task`） |
| 入力チェック違反 | 422 Unprocessable Entity | どの項目がなぜダメかを示す JSON | FastAPI（Pydantic）が自動で返す |

# ④データ設計
## Pydantic モデル ― API の入力と出力の形
「タスク」という1つのデータに対して、**入力用（作成）・入力用（更新）・出力用**の3つの形を定義します。

```python
class TaskCreate(BaseModel):   # 作成時に送ってもらう形
    title    : str = Field(..., min_length=1, max_length=255)
    completed: bool = False

class TaskUpdate(BaseModel):   # 更新時に送ってもらう形（全項目が省略可能）
    title    : str | None = Field(None, min_length=1, max_length=255)
    completed: bool | None = None

class Task(BaseModel):         # 返す形
    id        : int
    title     : str
    completed : bool
    created_at: datetime
```

- `TaskCreate` に `id` と `created_at` が無いのは、どちらもサーバー側で決める値だからです。クライアントには指定させません
- `TaskUpdate` は全項目を省略できます。送られた項目だけを書き換える「部分更新」に使います

## SQLAlchemy モデル ― データベースの1行の形
データベースの `tasks` テーブルの1行を、Python のクラスで表します（入門06で使います）。

```python
class TaskModel(Base):
    __tablename__ = "tasks"

    id         = Column(Integer, primary_key=True, index=True)
    title      = Column(String(255), nullable=False)
    completed  = Column(Boolean, default=False)
    created_at = Column(DateTime, default=lambda: datetime.now(timezone.utc))
```

| 列 | 定義 | 意図 |
|--------|------|------|
| `id` | `Integer, primary_key=True` | 主キー。データを追加したときにデータベースが自動で番号を振る |
| `title` | `String(255), nullable=False` | 空（NULL）を禁止する。長さは Pydantic の `max_length=255` と揃える |
| `completed` | `Boolean, default=False` | 作成直後は未完了 |
| `created_at` | `DateTime, default=...` | 行を作ったときの日時をサーバー側で記録する |

入力のチェックは Pydantic（違反は 422）が担当し、データベースの制約は「最後の砦」という役割分担です。

:::message
`Task`（Pydantic）と `TaskModel`（SQLAlchemy）は名前が似ていますが別物です。`Task` は **API の入出力の形**、`TaskModel` は**データベースの1行の形**です。データベースの構造をそのまま API の外に見せないために、あえて分けています。
:::

# ⑤処理フロー
`POST /tasks` を例に、リクエストが届いてから返すまでの流れを示します（完成版）。

```
クライアント → POST /tasks  { "title": "買い物" }
  → FastAPI が URL とメソッドから create_task を選ぶ（ルーティング）
  → Pydantic が TaskCreate の形かを確かめる（違反なら 422 を返して終わり）
  → get_db がデータベースとの接続（セッション）を用意して渡す（Depends）
  → TaskModel を作って add → commit（保存の確定）→ refresh（決まった id などを読み戻す）
  → Task の形に変換して 201 で返す
  → get_db がセッションを閉じる
```

`GET /tasks/{id}`・`PUT`・`DELETE` では、まず ID でタスクを探し、見つからなければ 404 を返します。この「探す → 無ければ 404」は3か所で必要になるので、`get_task` という関数に1つにまとめます。

# ⑥完成コードの全体構造
完成版の `main.py` は、次の順番で並びます。入門03以降は、この部品を少しずつ作っていく作業です。

```
main.py
│
├── import
├── データベースの設定: engine / SessionLocal / Base     ← 入門06
├── SQLAlchemy モデル: TaskModel（tasks テーブルの1行） ← 入門06
├── Pydantic モデル: TaskCreate / TaskUpdate / Task      ← 入門04・05
├── 依存関数: get_db（セッションを開いて閉じる）         ← 入門06

└── エンドポイント                                       ← 入門03〜05で増やし、入門06で書き換える
     ├── GET    /tasks
     ├── GET    /tasks/{task_id}
     ├── POST   /tasks
     ├── PUT    /tasks/{task_id}
     └── DELETE /tasks/{task_id}
```
