# タスク管理アプリの設計
第2章では、コードを書くまえの準備としてタスク管理アプリの設計を行います。

設計といっても難しいものではありません。「1件のタスクをどんな形のデータで表すか」「アプリが何を覚えておくか（状態）」「操作したら何が起きるか（処理の流れ）」を先に決めておく作業です。ここで決めたことを、入門03以降で順番にコードにしていきます。

:::message
この章は完成版（入門06まで終えた状態）の設計です。今の時点ですべてを理解できなくても大丈夫です。実装中に迷ったら、この章へ戻ってきてください。
:::

# ③データ設計
## タスクオブジェクト
1件のタスクは、次の形のオブジェクトで表します。

```js
{
  id       : string,   // crypto.randomUUID() で作る、重複しないID
  title    : string,   // タスク名
  completed: boolean,  // 完了フラグ
  createdAt: string,   // 作成日時（new Date().toISOString()）
}
```

`id` は「どのタスクを削除するか・完了にするか」を特定するために使います。配列の何番目か（インデックス）を代わりに使うと、削除で順番がずれた瞬間に別のタスクを指してしまうため、タスクごとに重複しない ID を持たせます。

## localStorage のキー
| キー | 値 |
|------|----|
| `tasks` | `JSON.stringify(tasks)` — タスク配列全体を JSON 文字列にしたもの |

キー名は `STORAGE_KEY` 定数として一か所で定義します。

## HTML の data 属性
タスク一覧のクリックを親要素でまとめて受け取るとき（イベントデリゲーション）、「どのタスクの、どのボタンが押されたか」を見分ける目印として、要素に `data-*` 属性を持たせます。

| 属性 | 付ける要素 | 値 |
|------|--------|----|
| `data-id` | チェックボックス / 削除ボタン | タスクの `id` |
| `data-action` | チェックボックス / 削除ボタン | `'toggle'` / `'delete'` |
| `data-filter` | フィルタータブの各ボタン（HTML に直接書く） | `'all'` / `'active'` / `'completed'` |

# ④状態設計
アプリが覚えておく値（状態）は、次の2つだけです。

```js
let tasks  = [];    // タスク配列
let filter = 'all'; // 'all' | 'active' | 'completed'
```

画面に出るものはすべて、この2つから作ります。一覧に何を表示するかは `tasks` と `filter` から、フッターの件数は `tasks` から、どのタブを強調するかは `filter` から決まります。

このように「データの置き場所を1か所に決め、画面はそこから作る」ことを**単一の真実のソース（Single Source of Truth）**と呼びます。画面（DOM）に直接データを持たせないので、状態と画面がずれる不具合が起きにくくなります。

:::message
「表示中のタスク」や「残り件数」は状態として持ちません。`tasks` と `filter` から描画のたびに計算します（入門05で詳しく扱います）。
:::

# ⑤イベント設計
「どの要素が、どの操作で、何をするか」の一覧です。

| 要素 | イベント | 処理 |
|------|----------|------|
| 追加フォーム（`taskForm`） | submit | 入力チェック → タスク追加 → 保存 → 描き直し。追加ボタンのクリックと Enter キーの両方が submit として届くので、イベントを1本にできる |
| タスク一覧（`taskList`） | click | イベントデリゲーションで、押された要素の `data-action` に応じて削除 / 完了切り替え → 保存 → 描き直し |
| フィルタータブ | click | `filter` を書き換えて描き直し（保存はしない） |

# ⑥主要処理フロー
## タスク追加
```
[追加ボタン / Enter キー → form の submit]
  → preventDefault()（ページの再読み込みを止める）
  → 入力値の前後の空白を除き、空文字なら何もしない
  → タスクオブジェクトを作って tasks に push
  → saveTasks() で localStorage に保存
  → render() で画面を描き直す
  → 入力欄を空にしてフォーカスを戻す（続けて入力しやすくするため）
```

## タスク削除・完了切り替え
```
[チェックボックス / 削除ボタンのクリック]（タスク一覧で受け取る）
  → event.target.dataset から id と action を取り出す
  → id が無い要素（<li> の余白など）のクリックなら何もしない
  → action === 'delete' → deleteTask(id)：指定 id 以外のタスクで tasks を作り直す
    action === 'toggle' → toggleTask(id)：指定 id のタスクの completed を反転する
  → saveTasks()
  → render()
```

## 起動時（データの復元）
```
[ページ読み込み]
  → loadTasks()
     → localStorage から読み出して JSON.parse
     → 配列ならそのまま tasks に入れる
     → 未保存（null）・配列以外・壊れた JSON なら空配列から始める
  → render()
```

## render() ― 画面の描き直し
```
render()
  → filter に応じて、表示するタスクを tasks から絞り込む
  → タスク一覧を空にする
  → 表示するタスクを1件ずつ createTaskElement() で <li> にして追加する
     （タスク名は必ず textContent で入れる。innerHTML に入れると XSS の原因になる）
  → フッターの件数を更新する
  → 選択中のタブにだけ active クラスを付ける
```

# ⑦完成コードの全体構造
完成版の `script.js` は、次の順番で並びます。入門03以降は、この部品を少しずつ作っていく作業です。

```
script.js
│
├── 型定義（Task）                ← JSDoc でタスクの形を書いておく（入門04）
├── DOM参照                       ← getElementById などを最初に一括取得
├── 状態変数: tasks / filter      ← 単一の真実のソース
├── STORAGE_KEY                   ← localStorage のキー名
│
├── addTask()                     ← タスクを追加（入門03）
├── deleteTask() / toggleTask()   ← タスクを削除 / 完了を反転（入門04）
│
├── saveTasks() / loadTasks()     ← localStorage への保存と読み込み（入門06）
│
├── createTaskElement()           ← タスク1件分の <li> を作る（入門04）
├── render()                      ← 状態から画面を描き直す（入門03〜05で育てる）
│
├── handleTaskSubmit()            ← 追加フォームの送信（入門03）
├── handleTaskListClick()         ← タスク一覧のクリック（入門04）
├── handleFilterClick()           ← フィルタータブのクリック（入門05）
│
└── イベントリスナー登録 + 初期化（loadTasks → render）
```

# まとめ
ここまでで、データ・状態・イベント・処理の流れという「設計」がそろいました。

特に大切なのは「状態設計」です。このアプリでは、画面の見た目はすべて `tasks` と `filter` の2つから作ります。どの操作も「状態を変える → `render()` で描き直す」という同じ形をしていることを、⑥の処理フローで確かめておいてください。
